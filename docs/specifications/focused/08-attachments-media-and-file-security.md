# Focused Specification 08: Attachments, Media and File Security

**Status:** DRAFT  
**Parent:** `../master-product-and-implementation-spec.md`  
**Gate:** gate-06-attachments  
**Requires:** gate-05-crdt-sync PASS  
**Related gaps:** GAP-016, GAP-020, GAP-033, GAP-035, GAP-043

---

## 1. Purpose

This specification defines attachment handling without weakening Inkstead's client-side encryption
model.

E2EE creates an important constraint: Django intentionally cannot inspect the plaintext file being
stored. File-security requirements must therefore be designed around that fact rather than
pretending a server antivirus scanner can inspect ciphertext.

---

## 2. Security principle

The server stores and serves opaque ciphertext.

It MUST NOT decrypt attachments for:

- thumbnailing;
- MIME sniffing;
- malware scanning;
- document conversion;
- indexing.

Any feature requiring server plaintext is outside the v1 privacy model.

---

## 3. V1 attachment scope

Preferred initial scope:

### First-class

- JPEG/PNG/WebP images;
- audio recorded/selected in browser-supported formats.

### Restricted/download-only candidate

- PDF.

### Deferred by default

- arbitrary executable/archive/document formats.

The exact list is a blocking review decision.

The master spec's broader file support is a SHOULD, not justification for accepting unsafe formats
without a defined client policy.

---

## 4. Image privacy and sanitization

For user-selected images, preferred default:

1. decode locally using browser image APIs;
2. re-encode to an approved image format;
3. strip EXIF/location/device metadata by default;
4. generate local thumbnail;
5. encrypt sanitized bytes;
6. store/sync ciphertext.

The UI MAY offer "preserve original file" later, but it must clearly explain metadata implications.

Client image decoding itself is an attack surface and must be browser-tested.

---

## 5. Audio

Browser-recorded audio is preferred because format/container is generated by a known API.

Selected external audio files require validation before local playback.

Do not auto-execute metadata scripts or external references.

---

## 6. PDF policy

If PDF support is included in v1:

- server stores ciphertext only;
- default client behavior SHOULD be download/open-on-user-action rather than automatic embedded
  preview;
- no server-side PDF processing;
- filename sanitized locally;
- CSP prevents remote resources from being fetched by Inkstead itself.

A browser PDF viewer remains part of the client trust boundary.

---

## 7. Generic file policy

Generic attachment support may be postponed.

If later enabled:

- treat as opaque download-only data;
- never render as HTML/SVG;
- never execute;
- do not claim malware scanning;
- warn users that Inkstead cannot validate encrypted generic files server-side.

---

## 8. ASVS file-scanning deviation

OWASP ASVS Level 2 includes server-side expectations around file validation/scanning.

For end-to-end encrypted attachments, the server lacks plaintext by design.

Inkstead must record this as one of:

- mitigated differently;
- not applicable due to architecture with documented compensating controls;
- accepted residual risk.

The ASVS matrix must explain the reasoning transparently.

Do not upload decrypted files to VirusTotal or any external scanning service.

---

## 9. Blob identity

Every attachment uses a random opaque blob UUID.

Meaningful filename/type/caption live in encrypted entry/attachment metadata.

Server-visible metadata should be minimized to:

- blob UUID;
- owner/vault;
- ciphertext size;
- upload state;
- ciphertext hash;
- timestamps needed operationally.

---

## 10. Blob key

Use the crypto spec's derived blob key or approved alternative.

No server access to blob key.

Each encryption operation uses authenticated context containing blob UUID and crypto generation.

---

## 11. Local staging

Before an attachment is shown as locally safe:

- plaintext input acquired;
- optional transform completed;
- ciphertext produced;
- encrypted blob committed locally;
- entry's encrypted attachment reference committed.

Quota failure must not leave the entry corrupt.

---

## 12. Size limits

Inkstead MUST set explicit limits.

Limits apply at:

- client selection;
- local encrypted staging;
- HTTP request;
- server model/storage;
- per-user/vault quota.

Exact v1 maximum is benchmark-dependent.

Whole-file in-memory encryption is acceptable only if mobile-memory tests prove the chosen maximum
safe.

Otherwise use authenticated chunking.

---

## 13. Chunked/resumable option

If chunking is required:

- each chunk has explicit index;
- each chunk is independently authenticated;
- chunk index/count belongs in AAD/manifest;
- random nonces never repeat under one key;
- encrypted manifest defines expected chunks;
- server can resume ciphertext upload without plaintext.

Protocol must be documented before implementation.

---

## 14. Upload API

Server validates:

- authenticated owner;
- vault ownership;
- blob UUID;
- ciphertext request size;
- chunk count/index if chunked;
- ciphertext hash;
- quota.

Server does not trust client MIME claims for security decisions.

---

## 15. Authorized download

Use private authenticated Django authorization with efficient Nginx/sendfile delivery of ciphertext
where supported.

Response from storage layer is ciphertext, generally `application/octet-stream`.

The browser decrypts after authorization.

---

## 16. Filename handling

Original filename remains encrypted.

On client download:

- decrypt filename;
- strip path components;
- remove control characters;
- bound length;
- sanitize for platform;
- use browser download attribute safely.

Server should use an opaque safe filename if Content-Disposition is needed for ciphertext.

---

## 17. Inline display

Only approved transformed image/audio types may display inline.

Never render:

- HTML;
- SVG;
- executable content;
- unknown generic file bytes

inside Inkstead's DOM.

---

## 18. Remote media

Inkstead MUST NOT auto-fetch remote media embedded in journal content.

This prevents:

- tracking pixels;
- IP leakage;
- external dependency;
- hostile content fetch.

A future explicit "import remote image" action would need separate validation and SSRF/privacy
review.

---

## 19. Orphan incomplete uploads

Server MAY delete incomplete ciphertext uploads after a conservative TTL.

Upload state must distinguish:

- staging;
- complete.

A crash before completion should be safely resumable or restartable.

---

## 20. Completed orphan blobs

Because the server cannot inspect encrypted entry references, it cannot safely infer that a
completed blob is unreferenced.

V1 SHOULD prefer storage leakage over accidental deletion.

Client-driven garbage collection may later:

- decrypt/scan live references locally;
- compare opaque server blob inventory;
- request deletion after a grace period.

Automatic completed-blob GC requires separate proof.

---

## 21. Permanent delete

When an entry is permanently purged, the client knows its referenced blob UUIDs and may request
their purge.

Server creates/retains purge markers as needed so stale replicas cannot recreate purged blob IDs.

Shared blobs are not a v1 feature, simplifying ownership.

---

## 22. Attachment URLs

Do not place meaningful filename/title in URL.

Use opaque route:

```text
/api/v1/blobs/<uuid>/
```

Authorization required.

---

## 23. Cache policy

Ciphertext downloads may be stored in encrypted IndexedDB intentionally.

Browser HTTP/Service Worker caches SHOULD NOT retain private blob responses unless the design
explicitly proves safe.

Plaintext Blob URLs are ephemeral and revoked when no longer needed.

---

## 24. Gate 06 tests

Minimum:

1. image attach offline;
2. image EXIF/location stripped under default policy;
3. corrupted image rejected safely;
4. ciphertext only in IndexedDB/server;
5. attachment upload interrupted/resumed/retried;
6. cross-user blob access denied;
7. oversized upload rejected at client/server;
8. generic HTML/SVG not rendered;
9. filename traversal/control chars sanitized on download;
10. decrypted blob not present in CacheStorage;
11. incomplete orphan TTL does not delete completed valid blob;
12. permanent purge deletes intended ciphertext;
13. plaintext canary absent from server storage/logs.

- exact file-size limit;
- whole-file vs chunked encryption;
- PDF inclusion;

- "preserve original" availability;
- incomplete-upload TTL;
- client-driven completed-orphan GC scope.

---

## 27. Exit criteria

Gate 06 passes only when:

- approved attachments work offline;
- plaintext never reaches server;
- unsafe formats cannot execute in Inkstead;
- ownership checks prevent IDOR;
- quota/upload failure is recoverable;
- E2EE versus malware-scanning tradeoff is explicitly recorded;
- no unresolved P1 attachment gap remains.
